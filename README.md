# Подбор

Telegram Mini App и десктопная CRM для автоподбора. Мобильный интерфейс находится в `index.html`, кабинет для компьютера в `admin.html`, генератор PDF в `pdf.js`. Серверная точка входа `supabase/functions/api/index.ts`.

## Десктопная CRM

- Обзор компании с количеством заявок, загрузкой ответственных и просроченными контактами.
- Таблица и доска заявок. Поиск по клиенту, телефону и автомобилю, фильтры по статусу и ответственному, архив, серверная пагинация по 100 строк.
- Создание и редактирование заявки, выбор ответственного, бюджет и пожелания, следующий контакт, несколько причин отказа и главная причина.
- Комментарии и история изменений. Изменение статуса, ответственного и архива сохраняется с автором на сервере в одной транзакции с заявкой.
- Команда. Добавление пользователей по Telegram ID, имя, роль, включение и выключение доступа. При удалении пользователя заявки сохраняются в компании без ответственного.
- Админ и владелец видят заявки своей компании. Менеджер видит назначенные ему заявки. Поставщику CRM недоступна. Эти ограничения проверяются сервером и SQL-функциями, а не только интерфейсом.
- При одновременном изменении заявки сервер проверяет `version` и возвращает конфликт вместо перезаписи чужой правки.

### Вход на компьютере

Открыть mini app из бота. В профиле или на экране кабинетов выбрать «Вход на компьютере», получить одноразовый код и ввести его в `admin.html`.

Код действует 5 минут, используется один раз, в базе хранится только его SHA-256. Браузерная сессия действует до 8 часов, её хеш хранится на сервере, а токен в `sessionStorage` вкладки. Выход удаляет текущую сессию. Активность пользователя и его роль проверяются на каждом запросе. Отключение доступа блокирует и уже открытые устройства при их следующем обращении к серверу.

## Общие заявки и перенос данных

Настоящие заявки из mini app и десктопа хранятся в `crm_requests`. Ответственный отделён от создателя. В мобильном интерфейсе можно создавать заявки и менять их статус, а на компьютере видеть общую очередь и переназначать работу.

При открытии CRM существующие пользовательские заявки из `user_workspaces` переносятся в общую базу. Демонстрационные автомобили не импортируются. По идентификатору источника перенос не создаёт дубли и не перезаписывает уже изменённые CRM-заявки. Исходное состояние сохраняется в `legacy_backup`. Источник привязан к компании, чтобы при смене компании старые данные не импортировались в новую. Не прошедшие проверку старые записи остаются в резервной копии.

В существующей установке пользователи первоначально объединены в «Основную компанию». Каждая учётная запись имеет одну компанию. Создание новых компаний и перевод сотрудников между ними пока не представлены в интерфейсе.

## Мобильный прототип

Сохранены кабинеты ролей, пример подбора Camry, сравнение вариантов, обзвон, расчёт цены, текст предложения и PDF с кириллицей. Поддерживаются PDF/PNG/JPEG-бланк, реквизиты, сохранение снимков версий КП и их повторное скачивание.

Демонстрационные настройки, цены, результаты демообзвона и версии примерных КП по-прежнему сохраняются персонально. Это не общий финансовый workflow дилера. Реальные CRM-заявки не записываются повторно в персональное демохранилище, они загружаются из CRM.

Вне Telegram мобильная страница работает как локальное демо без доступа к серверным данным. Десктопная CRM требует настоящего входа по коду. Получение кода не отправляет сообщений ботом.

## Что ещё не подключено

МойСклад, CRM сторонних компаний, сервис объявлений, ИИ-разбор, голосовое распознавание и рассылки поставщикам не подключены. Подбор Camry, рыночная аналитика и кабинет поставщика содержат явно отмеченные примеры. В примерах нет реальных фотографий.

КП по реальным вариантам новых CRM-заявок, общие настройки дилера, сетевые подтверждения цен владельцем и автоматические напоминания потребуют дальнейшей разработки. Дата следующего контакта и счётчик просрочки в CRM уже работают, но сами уведомления не отправляются.

## База и функция

SQL сохраняется в `supabase/schema.sql`, `supabase/workspace.sql` и `supabase/crm.sql`. Схемы применяются в таком порядке. Секреты не входят в репозиторий. Таблицы закрыты для `anon` и `authenticated`, вызовы идут через Edge Function с проверкой Telegram или серверной десктопной сессии.

CRM использует `app_companies`, `crm_requests`, `crm_activity`, `desktop_login_codes` и `desktop_sessions`. SQL-функции работают как `SECURITY INVOKER`, вызываются только ролью `service_role` и проверяют активность, роль, компанию и ответственного. Клиент не выбирает `p_actor`, его задаёт Edge Function по проверенному входу.

## Проверки

Нужен Node.js 24 или новее.

```sh
npm ci
npm test
npx playwright install chromium --only-shell
npm run test:browser
npm run test:crm
```

Браузерные проверки используют имитацию Telegram и Supabase, временный локальный сервер и тестовые данные. Рабочим ботам сообщения не отправляются. Сервер и браузер завершаются автоматически. `tests/crm-database.sql` проверяет реальные SQL-функции на временных данных и откатывает транзакцию. Не запускайте его на базе без предварительно применённой CRM-схемы.

## Публикация

GitHub Pages публикует статические файлы из `main`. Вместе с `index.html` нужны `admin.html`, `admin.css`, `admin.js`, `pdf.js` и каталог `assets`. Серверная функция развёртывается отдельно в Supabase. Деплой фронта не применяет SQL и не обновляет Edge Function автоматически.

PDF создаётся на устройстве с локально включёнными библиотеками, шрифтом и закреплёнными версиями. Содержимое КП не передаётся стороннему PDF-сервису. Лицензии перечислены в `assets/THIRD_PARTY.md`.
